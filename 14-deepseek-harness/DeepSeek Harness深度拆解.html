  // inject 接收的是服务名数组；cordis 等服务就绪后再执行回调
  ctx.inject(['greeter'], (ctx) => {
    // 这里拿到的 ctx 上已经有 greeter
    console.log('[消费者] 调用 greeter 服务：', ctx.greeter.greet('cordis'))
  })
}
Plain Chinese

  2. 它只声明“我需要 greeter”。
  3. Cordis 等该服务出现后才执行回调。
  4. 以后换 Provider，Consumer 不需要改代码。

Cordis：不是 Agent，而是 Microkernel

Cordis 负责组合能力，不负责替这些能力完成任务。职责清晰是可组合性的前提。

12 MIN
Cordis 内核
Plugin Mount / Unmount挂载插件，并在卸载时撤销它注册的副作用
Dependency通过 inject 等待服务就绪，而不是手工排序
Service / Event / Effect提供直接调用、松耦合通信和可逆资源生命周期
Shared Context让插件通过稳定 ctx.key 发现能力
Bash / Shell 执行由 Shell、Subprocess、Sandbox 等能力插件负责
Coding / Search / Web由模型工具与具体 Provider 负责
Agent Reasoning由模型与 Agent Loop 的组合负责
Session Strategy由 Session、Persistence、Projection 等插件负责
≈
定位

Cordis ≈ Microkernel；Plugins ≈ Runtime Capabilities。

Cordis 三原语

Service、Event、Effect 分别解决什么？

Service

系统现在具有什么能力？
  • ctx.tools：工具注册表
  • ctx.sessions：会话管理
  • ctx.llm：模型调用接口

Event

Runtime 中刚刚发生了什么？
  • agent/pre-step
  • agent/request
  • tools/pre-execute
  • session/event

Effect

这个 Plugin 注册了什么？
  • Tool 注册
  • Event Listener
  • Service 声明
  • Prompt Section
  • 卸载时完整撤销
✓
核心结论

Service 负责能力，Event 负责协作，Effect 负责生命周期。三者共同支撑 Plugin 系统的动态组合。

Reversible Effect

为什么可逆 Effect 很关键？

插件挂载初始化并注入资源
注册能力工具、事件、服务
运行时运行接管并使用注册项
插件卸载清理全部注册项
STAGE 1 / 4
Hot Reload配置变化后先干净卸载，再挂载新 Plugin。
Dynamic Tool运行时增减工具集，不留下旧注册。

Context 是插件共享的“总配电箱”

下面这段是 TypeScript，不是普通 JavaScript。interface 规定 Context 上有哪些基础服务；export 让其他文件可以引用它。

Exact Source
export interface Context {
  /** Isolation map: service name → scope label. Lookups for a name resolve within its label. */
  [symbols.isolate]: Dict<symbol>
  /** Intercept map: service name → config merged into that service's per-plugin config. */
  [symbols.intercept]: Dict
  /** The root context of the application (every child context shares it). @experimental */
  root: this
  /** Base URL used to resolve relative plugin/module specifiers, if the runtime sets one. */
  baseUrl?: string
  /** The event bus. Its methods are also mixed onto `ctx` (`ctx.on`, `ctx.emit`, ...). */
  events: EventsService
  /** The logging service. Call `ctx.logger(name)` for a named logger. */
  logger: LoggerService
  /** The reflection layer backing the context proxy (`ctx.get`, `ctx.provide`, ...). */
  reflect: ReflectService
  /** The plugin registry. Its methods are mixed onto `ctx` (`ctx.plugin`, `ctx.inject`). */
  registry: RegistryService
}
逐行白话
  1. export interface Context：公开一份名为 Context 的对象说明书。
  2. root：指向整棵插件树的根 Context。
  3. baseUrl?：可选的相对模块解析地址，问号表示可以没有。
  4. events：事件总线；logger：日志服务。
  5. reflect：服务提供与查找；registry：插件挂载与依赖注入。

Agent Inbox

为什么 Inbox 比 messages.append() 更完整？

Agent Input 不只是文本追加，而是具有不同语义、目标边界和唤醒规则的 Runtime Event。

followup() · 正常新任务

target: next-turnwakeup: trueopens new turn
Exact Source

    this.send(input, 'next-turn', true)
  }

  steer(input: UserMessage): void {
    this.send(input, 'next-step', true)
  }

  inject(input: UserMessage): void {
    this.send(input, 'next-step', false)
  }
Plain Chinese
  1. followup：放到下一 Turn，并唤醒 Driver。
  2. steer：放到最近的下一 Step，也会唤醒 Driver。

  4. 所以三者不是 messages 数组上的同一种 append。

安全分层

为什么 Permission、Guard、Sandbox 要分层？

案例：Agent 想执行删除文件、写配置或运行 Shell。四层分别约束模型行为、执行决策、不可逆安全规则和真实环境影响范围。

1
Prompt软约束：“不要删除重要文件。”模型可能遗忘。
2
PermissionAllow / Ask / Deny，可配置的执行策略。
3
Monotonic Guard硬不变量：一旦 Deny，不可被后续 Hook 反向放开。
4
Sandbox即使允许执行，也限制它能够影响的真实环境范围。
!
Monotonic Guard 的设计意图

安全规则一旦形成最终 Deny，不应该被后续普通 Policy 反向变成 Allow。

为什么不只用 Prompt？模型推理可能遗忘约束。Prompt 是软约束，不能作为安全保证。
为什么四层都要有？每层针对不同攻击面：越权请求、策略绕过、执行逃逸。

核心结论

Production Agent 的安全不能依赖模型“自觉”，必须由 Runtime Enforcement 逐层保证。

PTC 减少模型往返，但不绕过 Tool Pipeline

PTC 把多个工具作为生成 SDK 暴露给一段模型编写的 TypeScript 程序。程序中的每个子调用仍会重新进入完整的策略、Guard、执行和记录流水线。
